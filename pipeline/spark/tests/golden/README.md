# Golden fixtures (Module 52 §4)

`golden_windows.json` and `golden_anomalies.json` pin the *definitions* of the
window aggregation and the anomaly rules: what `weighted_delay` counts, when
`BLOCKAGE` may fire, how an `event_id` is shaped. The tests that read them are
`spark/tests/test_golden.py`.

These files are **hand-built inputs with hand-derived expected values** — they
are not generated by the code under test. A generated golden file only proves
the code equals itself.

## How to regenerate / extend

1. Add the case to the JSON by hand: `inputs` (events, window bounds, run id)
   plus `expected` (the values you derived on paper or in a spreadsheet).
2. Show the derivation in the PR description — an expected value nobody can
   re-derive is a future regression nobody can diagnose.
3. Run `make test` from `pipeline/` (needs no Docker, no Spark).
4. Floats are compared with `pytest.approx`; keep expected values to the
   precision of the hand derivation, not of the last computed bit.

Never "refresh" a failing golden by copying actual output into the file. A
red `test_golden.py` means the semantics changed; that decision belongs in an
ADR, not in a fixture edit.
