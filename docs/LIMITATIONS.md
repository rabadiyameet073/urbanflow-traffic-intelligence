# UrbanFlow AI — Limitations & Out-of-Scope Disclosures

> **Honesty by Construction:** UrbanFlow AI is a high-fidelity research simulation and operational decision-support tool.

1. **Simulation, Not Real Road Hardware:**
   UrbanFlow is designed to run in modern browsers and headless worker isolates. It is not connected to physical 170/2070/ATC signal cabinets.
2. **NTCIP-1202 Mapping Layer:**
   UrbanFlow implements an *NTCIP-1202-inspired object model* (mapping internal signal states to phase status group bitmasks). It is not certified for full NTCIP SNMP compliance.
3. **Simulated Watchdog:**
   Watchdog reversion timing is measured inside the software event loop (~100 ms). It does not substitute for hardware Conflict Monitor Units (CMU) or Malfunction Management Units (MMU).
4. **Single Intersection Scope:**
   The primary implementation models a busy 4-way, 8-lane intersection with protected lefts. Arterial corridor coordination across multiple intersections is reserved for future work.
5. **Precomputed Offline Vision Pipeline:**
   SAM 3.1 segmentation masks and Muse Image synthetic robustness assets are generated offline and loaded as committed assets to enable sub-second client loading without requiring a GPU in the live judge environment.

## Measurement Limitations

These are properties of the benchmark, not of the product, and they bound what the numbers in `RESULTS.md` are allowed to claim.

6. **Five held-out seeds.** Four of eight scenarios have a 95 % bootstrap interval that excludes zero; the other four do not resolve. The supported claim is "never significantly worse, significantly better in 4 of 8", not a headline speed-up.
7. **Survivorship in the delay metric.** `personDelayS` is computed over vehicles that exited. Vehicles denied at the approach appear in `deniedPct` and in the conservation check but not in delay, so a controller that denies aggressively can look good on delay alone. Both columns are always reported together.
8. **Preemption does not reduce measured ambulance delay.** In the detection-distance sweep all three paired intervals include zero (see `RESULTS.md` §5). Preemption relaxes the signal constraint, but the binding constraint in these runs is the physical queue ahead of the ambulance. The sweep's supported finding is the TIGHT/OK planning boundary at 19.5 s of required lead time, not a delay win.
9. **Sweep geometry confound.** The EVP sweep lengthens the approach with detection distance so the ambulance physically fits. A longer approach also stores more vehicles, so distance and storage move together; `laneLengthM` is written into every row of `ems-sweep.json` for that reason.
10. **Single topology.** All scenarios share the same four-approach, eight-lane geometry with protected lefts. Nothing here is evidence about corridor coordination, roundabouts, or networks with more than one intersection.
11. **One scenario misses its stated expectation.** `Stadium Surge Dump` was designed to demonstrate a surge advantage and instead produces a point estimate 12.3 % worse with an interval spanning zero. It is retained and reported unchanged rather than retuned.

## Specification Deviations

These are places where the build does **not** do what `instruction/` module 03 §5 asks, written down instead of hidden. Each is small, each is in the code as an explicit constant or comment, and each is queued in `state of agent/tasks.json`.

12. **EVP queue flush is a fixed two-vehicle placeholder.** Module 03 §5.2 specifies `queueFlushS = START_UP_LOST(2.0) + 2.0 × vehiclesAheadInLane`. The count has to be read from the simulator, and `EvpRequest` is a frozen wire contract that external gateways also fill in, so the build uses `2.0 + 2.0 × 2 = 6.0 s` for every request. A real queue longer than two vehicles makes the plan tighter than the reported `shortfallS`. Every published sweep number is produced under this model, and the sweep measures the plan status emitted by this code rather than re-deriving it.
13. **EVP required lead always includes clearance.** Module 03 §5.2 makes the yellow + all-red term conditional on the switch being a *conflicting* one. A request arrives without the current phase attached, so the build always adds 5.5 s. A preemption that lands on a phase which is already green is therefore reported as if it had to clear a conflict — the plan is pessimistic by up to 5.5 s in that case.
14. **`EMS_GREEN` is released at the stop line, not after the box.** Module 03 §5.3 holds the green until the vehicle has cleared the intersection box plus 2 s. The manager releases the hold as soon as the ambulance stops being observed in the approach lane, which is the stop-line crossing. The kernel's own yellow + all-red clearance (5.5 s) still covers the ~1.4 s needed to cross the 18 m box at 12.5 m/s, so this changes the reported numbers, not the safety property.
15. **One preemption at a time.** Module 03 §5.3 describes priority ordering across several emergency vehicles. The manager runs a single active plan: a same-phase request is served by the plan already running, a conflicting one is refused with `PREEMPTION_ACTIVE` and never replaces the vehicle being watched. There is no queue of waiting requests.
16. **The what-if does not clone mid-run state.** Module 04 §3.4 describes a digital twin that fast-forwards the *current* state. `evaluateProposalWhatIf` instead runs two fresh 5-minute simulations from the scenario's seed and config, which makes the A/B fair but means it answers "which parameter set is better on this demand", not "what happens next from here". A mid-run clone needs an engine snapshot/restore path that this build does not have.
17. **EVP timeline is a timestamped event log now (T22, closed 2026-11-02); the §5.4 vocabulary and milestone producers are the residue.** Module 03 §5.4 asks for an ordered record — `requested` → `accepted` | `rejected(reason)` → `preclear_started` → `green_granted` → `vehicle_exited` → `recovery_done` — where each entry carries both a sim-time and a wall-time. `EvpManager` now retains a capped lifecycle (`requested`, `accepted`, `rejected`, `cancelled`, `green_granted`, `stop_line_reached`, `recovery_started`, `recovery_complete`), each entry stamped with the simulated time at which it happened, streams it on every `EvpEvent`, and the panel renders the recorded transitions (last eight) instead of deriving everything live from `getStatus()`. Two honest deviations from the §5.4 wording remain: the exit milestone is stamped at the stop-line crossing, which is what the manager releases on (item 14), rather than at box clearance; and a wall-clock field cannot live in `packages/core` (Rule 07), so entries carry sim time only — simulated wall time is derived from `SIM_EPOCH_MS` where a timestamp is actually needed. In the kernel's own event stream, `emsMilestone` declares four members but only `spawned` and `boxExited` are ever emitted — `detected` and `stopLineReached` are contract members with no producer — and those events are drained straight into `MetricsEngine` inside `TwinWorld.tick`, so they never leave the worker and reach no audit path.
18. **The debug bundle is exportable (T23, closed 2026-11-02); it carries no `featureFlags` or `degradationLevel`.** Module 16 §6 asks for a one-click export producing `{appVersion, seed, scenarioId, inputLog, stateHash, userAgent, consoleLogs, kernelCounters, featureFlags, degradationLevel}`. The Audit panel's export button now builds that shape from real parts: the worker answers `exportDebugBundle` with the seed, scenario id, state hash, simulated time, kernel counters, the current adaptive parameters and the replayed input log as `{t, action, payload}`; the shell adds the build-time `__APP_VERSION__` Vite define, the wall clock, `navigator.userAgent` and a 50-line console tail; and `pnpm repro <bundle.json>` honours the recorded log by rebuilding a full `TwinWorld` from it before comparing hashes. The two omitted fields have no producers: the app has no feature-flag system and no named degradation ladder, and emitting placeholder values for them would violate Rule 00.
19. **zod↔Spark schema parity is not automated.** Module 12 §3.4 and Module 10 §8 both ask for a test that generates sample events from the zod contracts and runs them through the Spark `StructType`s declared in `pipeline/spark/urbanflow/schemas.py`. Those schemas are maintained by hand against `contracts.ts`; no test compares them, so a contract change can drift from the Python side silently. The TS-side half of that gate — the contracts freeze test — does exist and does fail on an unintended change.
20. **Saturation flow measures 1259 veh/h, below the 1500–2100 band.** Module 20 §10.4 asks for discharge flow under permanent green and saturating demand to land in 1500–2100 veh/h/lane. The engine measures **1259.0 veh/h** on `NB-TR` at 3000 veh/h of demand over 20 simulated minutes, and `packages/core/test/simulation_engine.test.ts` pins that measurement so a regression still fails. The cause is the approach boundary, not the car-following model: every arrival is admitted into the lane at 0.8 × the speed limit regardless of whether the lane is jammed, so each admission re-shocks the queue and the effective headway between discharges is longer than a saturated start-up. Fixing it means admission control at the boundary, which changes every arrival time and therefore every number in `RESULTS.md`, `results.json` and the EMS sweep; it is queued as task T25 rather than performed after the cut line. The supported claim is that discharge flow is *stable and reproducible*, not that it matches field saturation flow.
21. **The Kafka path has no producer, so it is unexecuted.** Module 23 §6 defines `make test` as the integration run — produce 60 s with a blockage injected at t = 20 s, assert eight lanes of metrics, read the Parquet back with pyarrow, see BLOCKAGE within two windows, print p95 latency, and restart from the checkpoint without duplicate windows. There is no producer in this repository, so nothing can publish to `lane-telemetry`: `make test-integration` and `make record` exit non-zero on purpose rather than print success. `make test` therefore runs the unit and contract suite, which is what actually executes here: window math, EWMA rules, `Settings` parsing and a parity test that fails when the Python constants drift from `contracts.ts`. The Spark job, the compose stack and the image build are written to module 23 but have not been run in this environment (no Docker daemon, no Kafka, no PySpark), so treat them as reviewed, not verified. Queued as T26.
22. **Diagnosis is text-only; the module 24 §7 annotated-PNG input is not wired.** The spec allows an annotated canvas PNG (lane labels, downscaled, ≤ ~1 MB) as an additional image input to Muse Spark, skipped when a provider lacks vision. What exists is the measurement path — the browser posts the structured `DiagnosisWindow` and the edge never accepts an image field — so no capture, annotation, encoding or vision-capability branch exists in the request pipeline. This narrows §7, not the safety case: numbers, causes and recommendations all still come from measured windows, and the evals dataset (`evals/`) is built from those same windows. Queued behind the cut line (Rule 15).
23. **The live-viewer WebSocket has no browser client, so the §3 reconnect/backoff table is server-side only.** Module 22 §3 specifies both ends of the transport. The Durable Object implements the full envelope validation, limits, strikes, close codes and a 30 s server ping, and `docs/API.md` documents the client contract (0.5→8 s backoff with jitter, `hello` on reopen). What does not exist is a caller: the web app streams through the in-tab worker and shares state through replay URLs and the share hash, so nothing in `packages/web` ever opens `/ws/:room`. Shipping a viewer client would be a new feature past the freeze, so the documented contract is the deliverable and the row is declared here rather than half-implemented.
24. **Committed benchmark artefacts were produced with a narrower method than Module 25 now prescribes.** The code has been brought to spec: the paired bootstrap uses B = 10 000 seeded resamples (§4, previously an explicit 2 000 in the runner), the EVP sweep is configured for 40 seeds per distance (§7, the committed `ems-sweep.json` measured 5), and `results.json` now embeds `seeds.train`, the frozen `params` and `bootstrapResamples` (§9) with `params.tuned.json` pinned by a parity test (§5.2). The *published numbers* in this repository — every CI bound in `results.json`, `ems-sweep.json`, `RESULTS.md` and the README — were generated before those changes, at the narrower settings and on 10-minute scenario blocks instead of §2's 60 + 5-minute design. Point estimates are unaffected by the resample count; CI endpoints will shift slightly on the next full run. Regenerating every artefact is a release step (`pnpm bench`), not something that can be patched by hand (Rule 00); until then this row is the disclosure. Censoring follows item 7: exited-vehicle delay with `deniedPct` reported alongside, not the §1.5 in-system inclusion.
25. **The web module map (module 30 §2) is not materialised as separate files, and `ui/app.ts` runs 2,564 lines against the <400-line guideline (§1.3).** The behaviours the split exists to serve are all present and correctly placed — the framework-light component pattern (§3 via the `h()`/`textContent` helper that bans `innerHTML`), the signals store contract (§4), the degraded states and global error handling (§6/§7, surfaced through the notice region in `main.ts`), the non-production `window.__uf` hook (§8), and manual-chunk build settings (§9). What was never done is carving `app.ts` into `app/shell.ts`, `app/router.ts`, `state/selectors.ts`, `state/actions.ts` and `ui/components/*`. That refactor moves working code without changing what users see, and doing it blind — no browser, no test runs allowed in this pass — is exactly the kind of change that breaks silently. It is queued as a mechanical follow-up for a session where the e2e suite can guard it (Rule 15).
26. **Module 31 §1/§7 overload is handled and now badged (closed 2026-11-02); the §7 dev overlay itself is not a separate surface.** The behaviours that protect the frame budget are implemented in `worker/sim.worker.ts`: the fixed-timestep accumulator clamps wall dt to 0.25 s, caps catch-up at `MAX_STEPS_PER_FRAME`, keeps at most one tick of debt when overloaded (so recovery is immediate, not a silent minute-long catch-up), and *drops* a frame rather than queueing when the buffer pool is empty — the §9 anti-patterns "queueing every frame when the UI is slow" and "freezing" are both avoided. The visible half landed too: `droppedRenderFrames` now rides every `KpisEvent` (a field added to the *worker protocol*, module 31 §2 — not to the frozen `contracts.ts`), and the footer performance badge reads *UI busy: N render frame(s) dropped* whenever the count is non-zero. What is still absent is a dedicated dev overlay counting drop rates per second; the badge is the shipped surface.
27. **Module 34's toolchain is enforced by `scripts/fitness.mjs`, not by ESLint/Prettier/dependency-cruiser/Playwright.** The spec (§3/§4/§5) names `pnpm lint`, custom `no-restricted-*` ESLint rules, `pnpm e2e`, and a Playwright CI job. The build deliberately does not add those dependencies (Rule 18: every new dependency is a supply-chain decision, stated in the `fitness.mjs` header), so the equivalent architecture guarantees are checked by purpose-built gates that need no new tooling — `fitness.mjs` covers purity (banned `Math.random`/`Date`/`window`/`fetch` in `core`), the dependency law, import cycles, the single-writer rule, the JS budget, secret-in-bundle, and the static header set; `tsc -b` with `strict` + `noUncheckedIndexedAccess` + `noImplicitOverride` covers type safety; vitest covers the unit/property/determinism suite. Two further §2 items stay unmet on purpose: `exactOptionalPropertyTypes` and `verbatimModuleSyntax` are `false` in `tsconfig.base.json` (enabling them repo-wide is a large, build-breaking-until-fixed change that cannot be iterated on in this pass, since no terminal or typecheck run is permitted), and there is no `packageManager` pin because the exact pnpm version is not recorded anywhere in the tree — guessing one would violate Rule 00 and Corepack would act on the wrong number. e2e/a11y/visual/perf browser gates are consequently not run; the a11y floor is enforced structurally (Modules 32/40) and via the `check-meta.mjs` meta gate now wired into `pnpm verify`.
28. **Module 41 §3 time-series charts (uPlot) are not implemented; the §2 "stale KPI" state and the honest-display, ribbon, explain, safety and EVP surfaces are.** §1's display rules are now enforced in code — per-KPI source/units, the single-run disclaimer (`kpi-disclaimer`), sign + arrow + colour deltas with the direction meaning stated as a `title`/`aria-label`, neutral parity, and missing values rendered as an em-dash *with a reason tooltip* — and the Gantt ribbon (§4), four-bar explainability panel (§5), safety badge (§6) and EVP stepper with the TIGHT shortfall banner (§7) all exist. What does not exist is the scrolling multi-series chart layer (queue/delay/throughput/CI/latency) because it would require pulling `uPlot` (or an equivalent) into the bundle, and Rule 18 treats every new dependency as a supply-chain decision that cannot be made blind in a no-build pass; the `manualChunks('charts')` slot in `vite.config.ts` is therefore currently a no-op because no `ui/charts/` module has been written. The §2 stale state is now an independent 1 Hz wall-clock watchdog in the store: if no `KpisEvent` has arrived for 2 s the footer badge reads *KPI feed stalled — values shown are the last measured*, and it clears on the next frame — the spec's stale indication expressed as an honest disclosure rather than dimming live numbers (closed 2026-11-02, alongside item 26's drop badge). The chart layer stays queued as post-freeze feature work (Rule 15), not a silent omission. (Module 40–43 deep pass, item 36: the §2 equity tiles (bus/bike delay) and the §2 LOS **outline-pattern** redundant encoding were added, so nothing in §2 is open here.)
29. **Judge Mode (§2) now has pause/skip controls, and its caption number comes from a provenance-commented bench copy rather than a runtime read of `results.json`.** The cold open (§1) is fully to spec — `ns-heavy-tide`, seed 42, 5× speed defaults in `state/store.ts`, persistent `SIMULATION ONLY` + `Identical arrivals (seed 42)` badges, prominent "Watch 90-second demo" and "Spawn ambulance" buttons, no blocking first-visit modal, and the `?judge=1` deep link auto-starting the tour in `main.ts`. The tour (`ui/judge/tour.ts`) steps at the exact 0/10/25/45/60/75/90 s boundaries with the §2 captions verbatim, `Esc` stops it, it ends in a fully interactive state, and reduced-motion swaps captions instantly (the overlay transition is disabled in `components.css`, and the in-app **Reduce motion** toggle now forces the same cut — item 36). The two previously unmet §2 clauses were closed on 2026-11-02: the overlay carries **Pause/Resume** and **Skip** buttons driven by a restructured tour controller that publishes `{active, stepIndex, caption, paused}` and shows a *Step N/6* pill; and the preemption caption is read from `ui/judge/bench-summary.ts`, a committed copy of the measured EMS-sweep mean (13.43 s, 95 % CI [4.34, 22.52]) carrying its provenance comment, rendered as "Preemption needs ~13 s to clear safely". It is not fetched from `results.json` at runtime because the `fitness.mjs` dependency law forbids `web` importing `bench` and a static host serves no such file at an app path — the number is real and measured (Rule 00 holds), but it is a snapshot that must be updated by hand when the benchmark is regenerated.
30. **Module 50 §1's compiler-enforced `core` purity (`lib: ["ES2022"]` with no DOM + `types: []`) is not enabled, because `core` is not yet fully environment-global-free.** The base config already turns on `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride` and now `noFallthroughCasesInSwitch`, and the string-literal-union / `import type` / `readonly` / branded-name conventions (§2, §7) are followed throughout. What blocks the strictest purity gate is `helpers/share-codec.ts`, which round-trips share links through `btoa`/`atob`/`Buffer`/`escape`/`unescape` — all environment globals that `lib: ["ES2022"]` + `types: []` would reject at compile time. Purity is therefore enforced today by the `fitness.mjs` grep gate (bans `Math.random`/`Date`/`window`/`fetch` in `core`) rather than by the compiler. Moving it to a compiler guarantee means rewriting that codec as a pure-TS UTF-8 ↔ base64url implementation with no ambient globals, and that rewrite must be proven by round-trip and fuzz tests plus a real `tsc` run — none of which can be executed in this no-terminal, no-browser pass (Rules 15/17), so the gap is declared rather than papered over with an unverified codec. `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `isolatedModules` and `noPropertyAccessFromIndexSignature` stay `false`/unset for the same reason (item 27): flipping them is a repo-wide change that only pays off once a typecheck can confirm it is green.
31. **Module 51 §3.1's `@layer` cascade is not adopted, so the §5 "no `!important` outside the reduced-motion block" rule keeps three justified exceptions.** The stylesheet already meets the rest of the module — semantic landmarks and `<button type="button">` throughout `ui/app.ts`, a first-focusable skip link and `<noscript>` fallback in `index.html`, logical `rem`/`fr`/`minmax()` sizing, single-class BEM-lite selectors, a tokenised global `:focus-visible` ring, a `forced-colors: active` block, `color-scheme: dark light` now declared on the root, and (from Module 40) no raw hex outside `tokens.css`. §3.3 is now met in full: a minimal `@media print` block hides the canvas, controls, dialogs and chrome and forces black-on-white so the Results content prints legibly, `content-visibility: auto` is set on the offscreen `dashboard-panels`, and a `.visually-hidden` utility exists as the accessibility-tree alternative to `display:none` the §6 anti-pattern table asks for. What is *not* done is wrapping `reset/tokens/base/layout/components/utilities/overrides` into real `@layer` blocks. That restructure changes effective cascade order across four files and can only be trusted once the rendered result is checked; with no browser and no build permitted, doing it blind is precisely the silent-breakage risk the freeze guards against (Rule 15). Until layers exist, the `!important` on the focus ring (`base.css`), the forced-colours outline, and the print block's `display:none` are load-bearing — `base.css` is linked *before* `components.css`, so without `!important` a component rule would win the cascade and the focus ring, High-Contrast borders and print-hiding would silently fail — so those three `!important`s stay, alongside the sanctioned reduced-motion block, rather than being removed without the layer guarantee that would make them safe to drop. Stylelint (§4) is likewise not added (Rule 18); the §5 checks are the manual greps documented in that module.
32. **Module 52's Python standards are now largely implemented, with two honest edges left open.** §2 is met in code: a custom `UrbanFlowError` hierarchy (`ConfigError`/`PipelineError`) lives in `spark/urbanflow/errors.py` and is re-exported from the package; the streaming job already logs through a JSON formatter (never `print`), reads config once into a frozen `Settings` dataclass, uses timezone-aware UTC datetimes, and confines IO to the entrypoint. §4/§5 are met: `integration` is a registered pytest marker (deselected by default in `pyproject.toml`), `tests/golden/` has a README stating the hand-derived-fixture regeneration rule, and `python -m urbanflow.cli run-stream` is a real argparse entrypoint (`spark/urbanflow/cli.py`) that delegates to the Docker `ENTRYPOINT`'s `main()` rather than a loose script. What stays open, deliberately: (a) `requirements-dev.txt` exists but pins only the two versions the Makefile already records (`ruff==0.6.9`, `mypy==1.11.2`); `pytest`/`pydantic`/`numpy` are left unpinned with an in-file `UNRECORDED` note because no exact version of them exists anywhere in the tree and inventing one would violate Rule 00 — they must be pinned from a real `pip freeze`. (b) `pip-audit` is now wired into CI over both requirements files, but as a `continue-on-error` step (same rationale as the grep audits, item 35): it has never run in this environment, so an unexpected advisory must not freeze an otherwise-green verify until a human has seen one clean pass. `ruff check`/`mypy --strict` remain configured-and-documented Makefile targets that fail soft rather than enforced CI gates (the Rule-18 stance in item 27), and the `vision/` package §3 describes is out of this repository's scope.
33. **Module 54 §1's `set -euo pipefail` + `IFS=$'\n\t'` header template is deliberately not applied to `scripts/smoke-live.sh`, and §7's `UF_*` Lite toggle has no code consumer.** The Makefile (`.DEFAULT_GOAL := help`, `.SHELLFLAGS := -eu -o pipefail -c`, `.PHONY`, `##`-documented targets, a `clean` that now prints what it deletes), the compose file (exact tags, `127.0.0.1` binds, per-service `mem_limit`, healthchecks + `service_healthy`, `restart: "no"`, `s3`/`hdfs` profiles, read-only repo mount) and the Dockerfile (`# syntax=` directive, pinned multi-stage, non-root, layer-cache ordering, OCI version/title/license labels) all meet their §2–§6 rules. `smoke-live.sh` keeps `set -uo pipefail` *without* `-e` on purpose: it is a reporting script that must run every check and print a pass/fail summary, so errexit would abort on the first failed probe — and forcing `IFS=$'\n\t'` would break its space-separated `for field in …` health-field loop. Both deviations are safer than following the template blindly, and the substantive rules (quoted expansions, arg parser that fails on unknown flags, stderr diagnostics, non-zero exit) are met. Separately, `UF_LITE` appears in `AGENTS.md` and this module's §7 table as the Lite-mode switch, but nothing in `pipeline/` reads it (the Lite runner is invoked directly as `pipeline/lite/urbanflow_lite.ts`), so it is not listed in `.env.example` — documenting an env var that no code consumes would imply a control that does not exist. `hadolint`/`shellcheck`/`yamllint`/`actionlint` (§1/§3/§5) are likewise not wired into CI, per the same Rule-18 decision.
34. **Module 55 §2's strictest Zod rules and the §2.8/§5 generated-artifact gates are held back by the contracts freeze and the no-terminal rule.** §1 is met on the security path: the EVP gateway verifies signatures over `canonicalJson(EVP_FIELDS)` (sorted-key canonical form), never raw `JSON.stringify` (ADR-012/013). Two gaps remain, both intentional. (a) `.finite()` is now on every numeric in `contracts.ts` and the edge copilot schemas (§2 rule 3) — a pure tightening that rejects `Infinity`/`NaN` and, because the bounds already excluded those on every bounded field, invalidates no value the gateway accepted before. What is *still* omitted on `EvpRequestSchema`/`SignedEvpSchema` is `.strict()` and per-string `.min()/.max()` length bounds, because adding them changes the accepted *shape* (unknown keys, empty/oversized strings) — a *contract change* that Rule 12 §5 gates behind an ADR, human approval, a `schemaVersion` bump, an N−1 reader and regenerated golden fixtures, none of which can be performed blind here; the module's security intent is instead met operationally by the edge's explicit `ALLOWED_KEYS` reject-unknown-keys list, request-size cap and timestamp window, so no unbounded or unknown-keyed payload is actually accepted. (b) `scripts/gen-api-schemas.mjs` correctly generates `docs/api/*.schema.json` from the frozen schemas via `z.toJSONSchema` (no new dependency, Rule 18) with a `--check` drift mode, and `pnpm api:check` exists — but the generated `docs/api/` files are not committed (emitting them needs a `pnpm api:gen` run) and `api:check` is not in the `verify` chain, because adding a gate whose artifacts cannot be produced in this pass would only turn CI red. Likewise §4 `markdownlint` and §5 `mmdc` Mermaid render-checks are not added to CI (Rule 18); `scripts/docs-check.mjs` (wired as `docs:check`) is the custom doc gate that does run.
